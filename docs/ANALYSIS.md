# Protocolo de nuevos análisis

Integración: scripts/save.js verifica el guardado; src/store.js conserva el historial y src/stats.js calcula las métricas. Reglas de liquidación en docs/SETTLEMENT.md.

Preferencia de comunicación: guardar los análisis, fuentes, selecciones y condiciones en la aplicación. No desarrollar análisis ni listas de pronósticos en el chat: dar solo una confirmación breve del guardado o del impedimento. Esta preferencia reduce texto visible, no la investigación ni los criterios de calidad. No inventar selecciones para completar una cantidad.

1. Usar fecha actual y Europe/Madrid. Consultar GET /api/predictions, /api/stats, /api/criteria y las auditorías relevantes. Revisar todo el historial, incluidas pérdidas, con N por mercado, liga, rango de cuotas, periodo y mes. Evitar conclusiones de muestras pequeñas; identificar correlaciones por ID de partido. Registrar cambios de criterio mediante POST /api/criteria con change, reason y evidenceIds.
2. Investigar internet con fuentes actuales: calendario e IDs, forma reciente con rivales y local/visitante, bajas, descanso y alineaciones. Separar temporada actual y anterior, registrar tamaño de muestra y datos ausentes. Córners: producción/concesión; tarjetas: disciplina y árbitro. No forzar extremos.
3. Preferir individuales, Bet365, cuota decimal ≥1,40. Nunca combinadas. No inventar cuota: si no es verificable, odds=null, oddsVerified=false, minOdds≥1.4 y presentar candidata condicionada. Una cuota verificada necesita oddsSource y oddsCheckedAt. Fuentes llevan url y accessedAt. No hay scraping ni acceso a la cuenta de Bet365.
4. Probabilidad solo con probabilityMethod defendible y datos reproducibles; de lo contrario null. Guardar razonamiento y availableData de lo conocido en la emisión. No rellenar estos campos con información posterior.
5. Habitualmente se pedirán 20 para hoy o hoy/mañana: entregar menos si no hay suficientes. No se generan selecciones por el mero inicio de la aplicación. Ligas: España, Francia, Alemania, Italia, Bélgica, Portugal, Irlanda, Championship y Champions.
6. Crear JSON con ID estable y encuentro ESPN verificado; usar `npm run save -- ruta.json` con la aplicación abierta. Este comando inserta por API y lee el historial para comprobar todos los IDs. Solo entonces entregar selecciones indicando IDs guardados. Un error exige corregirlo, no afirmar que se guardaron. Conservar todos los pronósticos. No etiquetar apuesta realizada sin confirmación expresa del usuario; importe/cuota desconocidos permanecen null.
7. Revisión basada en datos, no reentrenamiento automático. Beneficio/ROI reales solo con apuestas confirmadas, liquidadas, importe y cuota conocidos. Simulación 1u separada, solo con cuota recomendada verificada. No prometer beneficios ni sugerir aumentar importes para recuperar pérdidas.

## Modelo predictivo local: decisión del 14/09/2026

- Motor inicial: Python y CatBoostClassifier, aprendizaje supervisado sobre datos estructurados. No entrenar un modelo de lenguaje con textos de pronósticos. Almacenamiento exclusivamente en SQLite local; artefactos de entrenamiento locales y fuera de Git.
- Primer experimento tras aproximadamente un mes de recogida (10–20 selecciones diarias, unas 300–600 antes de depuración). Es una fecha para evaluar, no un umbral que garantice calidad. No hay entrenamiento ni automatización implementados todavía.
- Objetivo inicial: estimar la probabilidad de acierto de una selección. Empezar con mercados de liquidación binaria sin devolución (ganador, doble oportunidad y líneas de medio punto). No mezclar pendientes, nulas, anuladas o resultados ambiguos con pérdidas. Las líneas con posible devolución requieren posteriormente modelar también esa devolución antes de calcular valor esperado.
- Variables: mercado, selección y línea, liga, local/visitante, forma y estadísticas previas, descanso, bajas y cuotas verificadas disponibles al emitir. Conservar fecha de captura y valores ausentes. No usar datos posteriores al partido ni sustituir retrospectivamente las entradas originales. Incluir mercado como variable; no fragmentar inicialmente en un modelo por equipo o liga.
- Hardware comprobado con nvidia-smi: NVIDIA GeForce RTX 4070, 12282 MiB (12 GB de VRAM). CatBoost admite GPU NVIDIA en Windows. Para cientos de filas usar CPU por sencillez; probar GPU cuando el volumen lo justifique. La GPU no mejora por sí sola la precisión.
- Comparación obligatoria con una referencia sencilla (regresión logística regularizada y, cuando existan cuotas completas, probabilidades del mercado sin margen). Ajustar complejidad y regularización únicamente dentro del conjunto de entrenamiento. Semilla y versiones registradas para reproducibilidad.
- Validación cronológica, manteniendo juntas todas las selecciones del mismo partido. Reservar el tramo más reciente como prueba final sin utilizarlo para ajustar parámetros ni calibrar. Informar tamaño de muestra, log loss, Brier y calibración; precisión y rentabilidad por separado. No tratar varios logros del mismo encuentro como observaciones independientes.
- El historial de selecciones evalúa el filtro de recomendaciones; no representa todos los partidos. Ampliar posteriormente con encuentros no seleccionados y datos previos verificables para reducir ese sesgo.
- Guardar entradas diariamente. Reentrenar por lotes cuando haya nuevos resultados suficientes y comparar contra la versión vigente. Promover una versión solo con evidencia fuera de muestra; mantener el modelo experimental si no la hay. Cada predicción debe conservar versión del modelo, fecha de entrenamiento y variables utilizadas.

Referencias técnicas: https://catboost.ai/docs/en/concepts/cli-installation y https://scikit-learn.org/stable/modules/calibration.html.
